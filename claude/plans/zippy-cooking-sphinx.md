# 計画: 段 4(図の種類のプロファイルと、部品の札)(coord・2026-11-22)

## 0. Context

- 段 3a・3b で分かったこと: 誤りの大半は、図の書き方の約束を機械の決まりが知らなかったことから出た。決まりは表に出したが、**参照する規格・図の約束の表・項の表・記号の組み方が、別々の置き場と道具に分かれている。**
- 利用者の指摘(2026-11-22・決155): 図の記号は図の種類で違うので、**図の種類ごとに、参照する規格(JIS)やそのほかの資料を決められるようにする**ことが重要。
- 承認済みのサブセット様式 v1(`docs/04_サブセット様式_v1_20261021.md` §9)は、すでに「プロファイル」を定めている。分野(公開の規格に基づく)から顧客への 2 段で上書きし、顧客の知識は顧客域(管理外)に置き、版は人が承認する。**この段は、そのプロファイルを、実図面の道具で実際に使える形にする。**
- 元の計画(決130)の段 4 は「部品を目録にし、札(マニフェスト)を付ける」だった。プロファイルを先に置き、部品の札は、プロファイルを読む口(`profile_slots`)を持つ形で付ける。
- 狙い: 新しい種類の図が来た時に、「どの資料を見て、どの約束で読むか」を 1 か所で決められ、束を替えるだけで道具が動くこと。

## 1. この計画で承認いただくこと

1. **段 4 の中身と順**(§2)。
2. **プロファイルの型(profile.v0)を新しく作ること。** 型の中身は、S1 の終わりに案を出して、別にご承認をいただく(スキーマの変更は人手承認)。
3. **rev に、型と札の静的な読み(一般化した文書だけ・図は見せない)を 1 回頼むこと。** 知らせは ai-hub で自動。
4. **目安**: coord 6〜10 時間・トークン 20〜40 万(VLM の読取は増やさない)・利用者 25〜35 分(推定)。

## 3. プロファイルの型の骨子(S1 で案にして諮る)

| 部品 | 中身 | 今ある出どころ |
|---|---|---|
| `references` | 参照する資料の一覧。種別(規格・顧客の凡例・メーカーの図・社内の描き方の決まり・人の答え)、規格なら名と版と節、確かさ(顧客に確かめた・coord の仮定) | `selection.json` の種類 → 規格と節(決133)、予備情報の `standards` |
| `legend` | 記号の目録の選び方(どの規格のどの節から候補を出すか) | `selection.json` の部品の種類 → 節と語 |
| `vocabulary` | 項 → 部品の種類、項 → 接点の開閉の形 | `kind_map.json`・`form_map.json`(決152) |
| `rules` | 図の約束の表(決まりの入り切りと値)と、記号の組み方。**行ごとに出どころ**(決定の番号・確かめの回・coord の仮定) | `rules_scope.json`・`rules_compose.json`、決154・決155、T 字の答え |
| `pipeline` | 媒体(線のデータ・走査の画像)と、回す道具の並び | README の手順 |
| `open_questions` | 顧客・有識者への問いと、答えが入る先の行 | 問いの下書き 7 問 |
| `scope`・`approval` | 収録範囲の文、承認者と指紋 | — |

- 2 段: 図の種類のプロファイル(分野)→ 顧客のプロファイル(上書き)。既定値を持たず、欠け・不正は理由を付けて止める(様式 v1 §9)。
- 置き場: 中身は全て管理外(`data/`)。リポジトリには、型・空の雛形・人工の例だけを置く。規格に基づく分野プロファイルを共有域に置く条件(決17)は、許諾が未確認なので、この段では使わない。
- 道具(`scope.py`・`compose.py`・`propose.py`)は変えない。`profile.py` が、プロファイルから各道具の表を書き出す。

## 6. 止める条件

1. S3 で、プロファイルから書き出した表で回した出力が、今の出力と変わったとき(原因を調べて伺う)。
2. S2 で、今の表の行のうち、出どころを付けられない行が 3 割を超えたとき(coord の仮定が多すぎる。行を挙げて伺う)。
3. coord の時間かトークンが、§1 の 4 の目安の 2 倍を超えたとき。
4. 型の案に、様式 v1 §9 と合わない所が出たとき(様式の改めに当たるので、先に諮る)。

## 7. 検証

1. 型と整合: `tools/validate.py` が、人工の例と、管理外の 3 種類のプロファイルを通すこと。行に出どころの無い物・参照の欠けた物が、理由つきで落ちること(人工の壊した例で確かめる)。
2. 書き出しの一致: プロファイルから書き出した `rules_scope.json`・`rules_compose.json`・`kind_map.json`・`form_map.json`・`selection.json` が、今の物と中身で同じこと。それで回した A の 2 文書と C の 3 文書の出力の sha256 が、今と同じこと(実行の時刻を固定)。
3. 重ね合わせ: 顧客の側で 1 行を上書きすると、その行だけが変わること。決まりを 1 つ切ると、対応する試験(`test_scope.py`・`test_compose.py`)の期待どおりに出力が変わること。
4. 入り口: 残りの 3 種類の骨組みで、「目録に無い資料」「決まっていない約束」の数が出ること。
5. 既存の試験: `test_img.py` 10/10・`test_scope.py` 18/18・`test_compose.py` 18/18 が通ること。
6. 漏洩の点検: コミットするファイルで、禁止語の件数・作業の名と置き場の型・識別子の型・規格の文の断片が全て 0 件。`find proto -name __pycache__` が 0 件。プロファイルの中身(規格の節・顧客の約束)は、コミットしない。

## 8. 限界

- プロファイルは、決まりと資料を 1 か所に集めるだけで、読みの正しさは上げない。
- 図の種類は、今の語彙の 6 つ。束に入れるのは、設計用の図が手元にある 3 種類で、残りは骨組みだけである。
- 規格のほかの資料(顧客の凡例・メーカーの図)は、手元に無い。口(種別と欄)を作る所までで、中身は顧客への問いの答えを待つ。
- 段 5(封じた図での評価)は、この段の後に、方式(プロファイルの指紋とコードの sha256)と判定を固めてから、別に計画を諮る。
