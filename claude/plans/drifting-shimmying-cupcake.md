# 計画: 事例報告の検証の数え方の直しと、作業標準の確認票の取り込み(dcr・2026-10-31)

## 1. Context

あなたの記入を受けて、中身を画面に出さずに数だけを確かめた(読むだけ・費用 0)。

- **事例報告の記入票**: 記入は B の 1 件だけで、A・C・D は 0。E の確認者と日時はある。M3 の検査はすべて通った。
  - M3(置換)を回した。置換は B の名だけで、2 本で 10 件と 6 件。
  - M4(検証)は **V2(B の名の残り)だけが不合格**だった(20 件と 12 件)。ほかの V1・V3〜V8 は 0。
  - 原因(確定): V2 の当たりは、すべて置換で入れた印「[氏名]」の中にあった。印の外の当たりは 0。マスクは正しく、検証が自分で入れた印の中の字を数えていた。B の 1 件は 1 字の名で、その字が印の中の字と同じだった。
  - もう 1 つの穴(推定・今回の記入では起きない): `apply_mask.py` は A の後に B を当てる。A で入れた印の中の字が B の名と同じなら、B が印の中を置き換えて印が壊れる。D の印も同じ。
  - M5 の門(LLM に送る)は閉じたまま。
- **vision の確認票**: 59 行すべてに記入がある。記入欄の外は、作り直した票と 59 行とも一致した(行の対応は崩れていない)。確認者と日時もある。
  - 記入の種類は、文字 11・記号 14・「?」8・画像 26。
  - 記号は 14 行とも V だった。どの行も、vision の読みが 3 回とも一致している(票で 2 通りに見える 3 行は、空白などの違いだけ)。
  - 画像 26 行の置き場: 25 行は、節の中で項に入らない行。1 行は、1 行だけの項の頭の行。
- **作業標準の書き出し(E4)は、契約に決まっていない点がある**(§4)。今の契約の作業標準は、`WorkProcedure` と `Point` しか受けない。

## 2. 手順 A: 事例報告の検証の直し(道具の直し・費用 0)

1. **`scripts/dcr/case_mask/verify_mask.py` の `verify()`**: V1〜V4 の残りを数える前に、マスク後の文字から 4 種の印(`PLACEHOLDERS`)を除く。印の外だけを数える。V5(印の数 = 原文の出現の数)は今のまま。
2. **`scripts/dcr/case_mask/apply_mask.py` の `mask_text()`**: 置換の間は、印を私用領域の 1 字(U+E000〜U+E003)にしておき、最後に印へ戻す。これで、後の規則が印の中を置き換えなくなる。原文に私用領域の字があれば、その単位で止める(件数だけを出す)。
3. **selftest に足す**(合成のデータだけ):
   - B の名が印の中の字と同じとき、V2 が 0 で合格し、印が壊れないこと。
   - A で入れた印の中の字が B の名と同じとき、印が壊れないこと。
4. コミットしてから M3 を回し直し、M4 を回す。
   - `units_masked.jsonl` は今回と同じ sha256 になる見込み。今回の記入では A と D が空で、B は 1 回の置換で済むため。
   - 画面には件数と合否だけを出す。あわせて、B の置換の数と、残す接尾の前で残した数を出す。あなたの全読と照らせるようにするため。

**確かめていただきたいこと**: B の 1 件は 1 字で、置換の印「[氏名]」の中の字と同じ字でした。B は、その 1 字そのものを印に置き換え、前後の字は残します。意図と違っていれば、記入票を直してください。M3 は台帳から毎回作り直すので、直した後に回し直せます。M5(LLM へ送る)は別の計画で、この計画では送りません。

## 3. 手順 B: vision の確認票の取り込み(新しい道具・費用 0)

1. **新しい道具 `scripts/dcr/ws_vision_apply.py`**: `ws_vision_review_sheet.py` の作り方で票を作り直し、記入欄の外を行ごとに照らす。1 行でも合わなければ止める。そのうえで、行ごとに記入を次の 5 つに分ける。
   - **文字** → 是正の値 = 記入(`fix_method: manual`)。
   - **O・T・V** → 是正の値 = その読み。V は `vote.jsonl` の多数の読み(`text_vision`)を使う(`fix_method: manual` = 人が選んだ)。
   - **?** → 是正の値なし(読めない・`illegible` の材料)。
   - **画像**(「文字ではなく画像」を含む・NFKC と空白を除いて判定) → `not_text`(要素の文字から除く材料)。
   - **空** → 止める(今回は 0)。
2. **出力**(git 外):
   - シートごとの `<sha16>/vision_out/review.jsonl`(行 ID・番号・判定・是正の値・方法)。
   - `_vision_review_applied.json`(票の sha256・作り直した票の sha256・確認者と日時の有無・判定ごとの数)。
3. 画面には、判定ごとの数と sha16 だけを出す。dcr は票の中身を開かない。`fields.json` と `lines.jsonl` は書き換えない。是正は、書き出し(E4)が別欄の `fixed` で持つ。

## 4. 手順 C: E4 の契約の未定の点を kgb に頼む(連絡文・値なし)

dcr の作業標準の出力の欄は、記録 §7 で公開済みの欄名で書く。値・件数・どの欄に当たりがあるかは書かない。kgb への req(cc coord)で、次の 4 点に案を添えて、受け方を決めてもらう。契約の変更になるので `needs_user_approval: yes` とする。

| 点 | dcr の案 |
|---|---|
| (1) 節の中で項に入らない行(`sections[].text_lines`) | 節ごとに、続く行を 1 つの `Chunk` にする。eid は `s<節の順>#<順>`(I10 の書式に足してもらう) |
| (2) 是正した節の見出しと、語彙の照合 | `Point.attrs` に `section_fixed` を足し、照合は是正の値で行う。kgb の I11・K4 の検算が `section_fixed` を見る |
| (3) 人が「文字ではなく画像」とした行 | 要素の `prov.line_ids`・`raw`・`norm` から除く(説明書の束を除いたのと同じ形)。頭の行が画像の項は出さない(eid の番号は詰めない)。除いた数と票の sha256 は `_meta` に残す |
| (4) 図中の行と表の行(`figure_text_line_ids`・`table_line_ids`) | `_meta.searched` に「未対応」と書いて出さないか、`Chunk` にするか、kgb に決めてもらう |

- kgb の答えと dec の後に、E4 の書き出しの計画を出す。そこには、次のことを入れる。
  - 2 読みの一致・vision の多数決・人の確認の `fixed` と `fix_method`
  - `_meta.llm` の 21 回の回ごとの設定
  - 見出し欄の `illegible` の扱い
- それまで、書き出しの道具(`export_kgb_input.py`)は触らない。
