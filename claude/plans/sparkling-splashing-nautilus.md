# 計画: 文書の階層の入力の契約 v0.7 と、API 1.1 の欄の案(決168 の段 1)

## 1. 背景(Context)

- 決138・決141・決153 で、文書の階層を「深さの数字 + 種類 + 原本の印」で持ち、附則・別表を章と同じ段の見出しにすると決めた。決168(2026-11-20)で、5 つの段の順で作り直すことが承認された。kgb の手番は段 1(契約 v0.7 と API 1.1 の欄の案)である。
- 段 2 は、凍結済みの 4 本(作業標準 2・規程と基準 2)を、演習の一時の Neo4j で受ける試しである(正本には入れない)。段 2 の前に、kgb の入力の検査と投入の道具が v0.7 を受けられる要がある。
- 今の型(確定・コードで確かめた):
  - 規程などは節(Section)の木。種類の語(`attrs.kind`・7 語)と、親への辺(PART_OF)を持つ。
  - 作業標準の項(Point)は、作業標準の節の下に平らに並ぶだけで、入れ子の辺が無い。
  - 深さ・種類・原本の印の欄は無い。v0.6 の型は、complete の節に種類の語を求める。
  - API 1.0 は、節の種類の語を返していない。
- 利用者の選び(2026-11-20・この画面): 親を仮に置いた行は、印だけで持つ(欠けの節点は立てない)。
- 本計画は、絶対規則 4 のスキーマの変更の承認を兼ねる。API 1.1 の作りは段 5 で別に諮る。

## 2. 入力の契約 v0.7(文書だけ・事例報告と図面は今のまま)

### 2-1. 足す欄(dcr が書き出す)

| 欄 | 置き場 | 中身 | 必須 |
|---|---|---|---|
| `attrs.block`(種類) | Section・Point | `heading`(見出し)・`item`(箇条)のどちらか。規程の号やイなども、節のまま `item` にする | 必須 |
| `attrs.marker_raw`(原本の印) | Section・Point | 行頭の印を原本の字のまま(第 3 条・(1)・イ・3-2-1・附則・別表第 1 など)。印の無い行は持たない | 印のある行だけ |
| `attrs.parent_basis`(親の決まり方) | Section・Point・Chunk | `rule`(決まりで決まった)・`human`(人の答え)・`provisional`(決まらず、すぐ上の行の内訳として仮に置いた・決141 と決168 §3) | 必須 |

- Chunk の種類は本文、Table と Figure の種類は表と図として、kgb が補う(dcr は書かない)。
- 種類の 4 つ(見出し・箇条・本文・表と図)は決138 のとおり。

### 2-2. 深さ(kgb が決める)

- dcr は深さを書かない。kgb が親の鎖から決定論で数える(文書 = 0)。作業標準は、手順(WorkProcedure)= 0・作業標準の節 = 1 から数える。
- 節点の属性 `a_depth` に入れる(節・作業標準の節・項・塊・表・図)。

### 2-3. 親(今の辺のまま・1 つだけ広げる)

- 作業標準の項の入れ子は、項から親の項への `PART_OF` で持つ(今は節どうしだけの辺を、項どうしにも広げる)。
- 入れ子の項も、今のとおり作業標準の節から `HAS_POINT` を持つ。手順の口の平らな並びは変えない。道(上の節の並び)は `PART_OF` を先にたどる。
- 作業標準の節より深い見出しは、種類が見出しの項として持つ(作業標準の節の型を増やさない)。

### 2-4. 見出しの種類の欄に値の無い節(決153)

- complete の節でも、種類の語を null にしてよい。ただし、種類が見出しで、原本の印が在ること(附則・別表など)。新しい語は作らない。グラフでは `a_kind` を持たず、`a_marker_raw` に原本の語が入る。

### 2-5. 入力の検査に足す照らし(v0.7 だけ)

- 種類と親の決まり方の値が、決めた語の内か。
- 種類の語が null の complete の節は、種類が見出しで、原本の印が在るか。
- 項の `PART_OF` の先が同じ本の項で、輪にならないか。親の鎖が文書まで届くか。

## 3. グラフ(属性を足すだけ・節点の型は改めない)

- `a_block`・`a_marker_raw`・`a_parent_basis`・`a_depth` を足す。辺は項どうしの `PART_OF` だけを足す。
- 親を仮に置いた行は、`a_parent_basis = provisional` の印だけで持つ(利用者の選び)。欠けの節点は立てない。

## 4. API 1.1 の欄の案(作りは段 5・足すだけ)

| 口 | 足す欄 |
|---|---|
| 節の口(`/v1/doc/section`) | 節と各項目に `depth`・`block`・`marker_raw`・`kind`(null を許す)・`parent_basis`。項に親の項の id |
| 手順の口(`/v1/doc/procedure`) | 項に `depth`・`block`・`marker_raw`・`parent_basis`・親の項の id。平らな並び(順)はそのまま |
| 文書の検索・表の一覧の道(`path`) | 道の各段に `depth`・`marker_raw`。道のどこかに仮の親があれば、その段に `parent_basis = provisional` |

- エージェントの道具の説明に新しい欄を書くなら、文面の第 2 版の承認が要る(段 5 で諮る)。

## 5. 作業の順

1. 承認の後、骨子を dcr に送る(先の送りは、再起動で dcr の名が変わり届いていない)。dcr の読み手の直しの計画(dcr の画面)と食い違いが無いかを合わせる。
2. 設計書(新: `docs/設計_文書の階層の契約_v0.7_kgb_20261120.md`)と、型のファイル `config/schema/kgb_input_v0.7.{element,meta}.schema.json` を書く。
3. `scripts/kg/check_input.py`(v0.7 の照らし・`PART_OF` の項への広げ)と `scripts/kg/ingest.py`(深さを数える・Chunk・Table・Figure の種類を補う・項の `PART_OF`)を直す。合成の v0.7 の本を selftest に足す。
4. 統制の台帳への登録は、演習と正本の入れ替えの前に dec で行う(今回の演習は台帳の外で記録だけ)。
5. rep(dcr・acc・coord 宛て)。acc には、深さの数え方(文書 = 0・作業標準は手順 = 0)を、期待の第 2 版に合わせるため知らせる。
6. dcr の 4 本の書き出しの後、演習の一時の Neo4j で受ける(段 2・LOCKS に予約・正本には入れない)。

- dcr との合わせで欄が変わる時は、この画面で諮り直す。

## 6. 確かめ

- `check_input.py selftest`・`ingest.py selftest`: v0.7 の合成の本が通る。照らしの外れ(決めた語の外・種類の語が null で原本の印が無い節・項の輪・本の外の項への辺)で止まる。v0.6 以前の本は今のとおり通る(後ろ向きに合う)。深さの数えが合成の木と合う。
- 正本は変えない。API の selftest は今のまま通る(API の作りは段 5)。
- 監査と検査: `audit_qa.py run`、漏れの検査(worktree と diff の行の数 = 三点の numstat・コミットの文)、QA の写しの照らし。merge は単独で回す。

## 7. しないこと

- 正本の入れ替え(段 4)・API 1.1 の作り(段 5)・エージェントの文面の変更。
- 凍結の前の本(説明書 e18328e109441faf・事例報告)を段 2〜4 に入れること。
