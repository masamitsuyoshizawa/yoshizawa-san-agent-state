## 2. 解析の手段

**共通の下地**(`lines.py`・決定論): まず頁ごとに文字層の出自(不可視の描画モードの比率・頁全面の画像の被覆)を判定して、経路を分ける。原文 `text_raw` は変えない。正規化(NFKC・字間の空白の除去)は別欄 `text_norm` に持つ。柱・頁番号・表の中の行には印を付ける。自己点検は次の 2 つ: 行を連結した文字と、頁全体を取り出した文字が一致すること。2 回の実行で sha256 が一致すること。

**書き出し**(`export_kgb_input.py`・`export_ws.py`・`export_case.py`・決定論): kgb の入力の契約は次のように進んだ。

- v0.2(決6・決9)

## 5. ノウハウ(試行錯誤の過程)

### 5-1. 経過

1. **下見(10-29・0 USD)**: 当初は phase12 の型(しおり・字の大きさで見出しを取る)を当てる想定だった。しかし計測すると、しおりは無く、字の大きさも一様で、どちらも外れた。文字層の出自を最初の門にし、見出しは番号の型と位置で取る形に変えた。原文を文脈に出さずに様式を設計するため、行を字種の形に写す道具(`shape_page.py`)を作った。
2. **受入の独立**: dcr は、規則が出たことを知らずに読取の値を記録に書いた。値を git の外へ移し(決4 (4))、以後は件数の形だけを書く。
3. **作業標準の誤字**: 2 読みだけでは是正に足りなかった。食い違った行だけを vision に回す 3 段にした。最初の 1 回で usage を実測し、見積りを 0.570 から 0.327 USD に直してから残りを送った。複数の画像を付ける問いの欠けは番号の検査で見つけ、思考の既定有効は後から見つけて規則にした(決21)。
4. **書き出し**: 演習で K2 の不一致が出た(決22)。原因は根拠の範囲の持ち方で、原文の書き換えではなかった。これを受けて契約を v0.3(行 ID の並び)へ上げた。版を上げるたびに、足した欄を除いた sha256 が前の版と同じことを門にした。
5. **事例報告**: LLM による氏名抽出をやめ、決定論の候補と人の全読に置き換えた。検証の穴(自分の印を数えた)と、見本が写された件を経て、記入を web 画面に移した。M5 は守り(入力の sha256・プロンプトの sha16 を指す dec)を足してから送った。
6. **結合**: 鍵の在り処の思い込みを、件数の食い違いで見つけた。組として読む形に直し、契約 v0.5 に入れた。

### 5-2. 一般化できる点(札 G の候補・確定は未)

1. 最初の門は文字層の出自。原文は不変にし、正規化は加法の別欄に置く。
2. 見出しは番号の型 + 位置 + 単調性で取り、段の抜けは番号の重なりで検出する。目次は別の関数で読み、独立の照合に使う。ただし、抜粋かどうかを刷り頁で先に測る。
3. OCR の是正は 2 読みの差分 → 差分の行の切り抜きだけを vision に送る → 多数決 → 人。
4. LLM に送る前のマスクは LLM なしで回す。台帳を正本にして毎回作り直し、置換とは別の数え方で照らす。
5. 送る直前に、入力の指紋と承認の記録を照らす。最初の 1 回で費用を実測し、累計 + 次の最悪で打ち切る。
6. 下流の検査の関数を上流で先に呼ぶ。版を上げるときは、足した欄を除いた不変を門にする。
7. 人の記入はボタンの画面にし、記入の結果をその場で数と文脈で見せる。

### 5-3. 新しい同種の文書を自動で扱うスキルへの示唆(推定)

- 様式ごとに「門・読み手・契約・自己点検」をひとそろいにする。顧客固有の語彙・型(欄名・管理番号の型・節名)は設定ファイルに外出しする。
- 「0 件」は照合してから信じる。閾値の際は件数の食い違いで見つかる。
- 人の手番は短く・確認票で残し、判断は dec に記録する。
