# 計画: V3 語彙 DB の設計書を起草する(2026-09-21)

## Context

**なぜ書くか**: 利用者が V3 の計画を承認し(`dec 20260921-0919`)、coord が語彙 DB の設計書の起草を dkb へ依頼した(`req 20260921-0921`)。設計書は 3 本に分かれ、fed が API、dkb が語彙 DB、bkb が受入条件を書く。3 本が揃ったら rev がレビューし、利用者が設計の中身を承認してから実装に入る。

**何が決まっているか**: 置き場は別 DB(`dec 20260919-1229`)。台帳キー `vocab` / `vocab_ec2` は実装済み(`f570281a`)。移行は JSON 廃止の 4 段(`dec 20260919-1303`)。**設計書は「どんな形にするか」を一から決めるのではなく「既にある形をどう移すか」を決める**。

**本計画で書くのは設計書 1 本だけで、コードには触らない。** 実装は設計の承認後。

## 調査で分かった、設計の核心になる 3 つの事実

**すべて本日 read-only で実測した。設計書の根拠になる。**

### (1) 設備辞書の `kind` は、関係の型にほぼ写せる

`kg_api/kb/config/dict_equipment.json` の `aliases` 2,293 件は `kind` を持つ。

| `kind` | 件数 | 写す先(案) |
|---|---:|---|
| `variant` 1,309 / `abbr` 412 / `halfkana` 187 | **1,908** | **`SYNONYM_OF`** |
| `model` | **272** | **`MODEL_OF`** |
| `product` 107 / `part` 6 | **113** | **`PART_OF`** |

**限定**: **`PART_OF` に相当するものが 113 件しかない。** 問 1 が「(a)-(d) すべてが検索対象」を求めるのに対し、部分‐全体の関係はほとんど入っていない。**設計書では「型は写せるが、`PART_OF` の中身はこれから足す必要がある」と書く。**

### (2) 現象辞書の `basis` は「作られ方」で、`source` には写せない

`dict_failure_modes.json` の `surface_map` 893 行の `basis` の値:
`LLM判定案` 316 / `LLM判定案・新述語` 305 / `設備+述語分解` 159 / `症状一致` 51 / `述語一致` 27 / `設備のみ` 19 / `設備+症状分解` 16。

**どれも「どう作ったか」であって「どこから採ったか」ではない。** 設備辞書の `source`(`B:1` / `glossary` / `term_index` …)に相当するものが無く、**`basis` から機械的に導けない**。

**設計書では「揃えるなら `source` を新たに採る必要がある。`b_freq` があるので出どころは B 本文だが、どの記録かは持っていない」と書く。**

### (3) **現象の階層は、既存の欄では表せない** — 最も重要

入れ子の 4 段を実データで見ると、同じ階層が別々の欄に散っている。

| 語 | `equipment` | `predicate` | `symptom` |
|---|---|---|---|
| 重故障(86 回) | — | **故障** | — |
| 踏切重故障(63 回) | — | — | **踏切重故障**(自分自身) |
| 電子踏切重故障(9 回) | **dict:eq:3756a80e** | **故障** | — |
| 電子踏切重故障2(2 回) | **dict:eq:3756a80e** | — | **重故障2** |

**「踏切重故障」は `symptom` に自分自身が入っており、分解されていない。** 問 7 が求める「大きなまとまりから条件別に絞る」を、現状の欄では表せない。**階層を持つ関係(または欄)の新設が要る。これが本設計書の中心の承認事項になる。**

## 成果物

**`docs/設計_V3_語彙DB_20260921.md` 1 本のみ。**

構成は `req 20260921-0921` §3 の 8 節に従い、各節を次の方針で書く。

| 節 | 書くこと | 根拠 |
|---|---|---|
| **1. 設備辞書をどう移すか** | `source` のリスト(全 2,293 件が list・要素数 1 が 1,207 / 2 が 1,075)を**別ノードにする案と配列プロパティにする案**を並べ、**fed の「印は `source` まで出す・切り口ごとに内訳を出す」が軽く書けるか**で比べる | 本日の実測 |
| **2. 括り方を関係の型で表す** | `kind` → `SYNONYM_OF` / `MODEL_OF` / `PART_OF` の写し方(上表)。**`PART_OF` が 113 件しかないことを限定として明記** | 上記 (1) |
| **3. 現象の階層をデータとして持つ** | **既存の欄では表せない**ことを (3) の表で示し、階層の関係を新設する。**比較表の 4 行は未回答なので、階層の段数も「回復を含めるか」も後から変えられる形にする** | 上記 (3)・`rep 20260919-1159` |
| **4. 2 つの辞書の形を揃えるか** | 揃えることを勧める。**ただし `basis` から `source` は導けない**ので、新たに採るか「不明」と書くかを承認事項にする | 上記 (2) |
| **5. `status` の限定** | `164号ポイント → 軌道回路` が `confirmed`、`164号 → 転てつ器164号` が `proposed`。**正しい対応が未確定で誤った対応が確定済み**。`status` 単独では信頼を語れない | 本日の検算 |
| **6. 移行の 4 段** | `dec 20260919-1303` のとおり。**第 3 段(GOVERNED から外す)は統制の範囲を狭めるので別に利用者承認** | 既決 |
| **7. 台帳と G0** | `vocab` は台帳にあれば照合し無ければ何もしない(実装済み `f570281a`)。**語彙 DB の digest を測定の記録に併記する** | 既決・`rep 20260919-1252` |
| **8. 前提が変わったら変わる箇所** | **データ側で変えられる箇所**(階層の段数・別名の追加・`status` の変更)と**スキーマを変えないと動かせない箇所**(関係の型の追加・`source` の構造)を分けて書く | `dec 20260921-0919` |

### 付けるもの

- **承認事項の一覧**: (a) スキーマの新設(ラベル・関係の型・プロパティ)、(b) 現象辞書に `source` を足す、(c) 現象の階層の関係の新設、(d) 移行の第 3 段。**(c) は coord の挙げた 3 つに私が足す分。**
- **fed の文書との接点**: 「語彙 DB が API に何を渡せるか」を 1 節。食い違いは `req` で coord へ上げる。
- **限定の節**: 実測の範囲(`confirmed` 262 語・対 29 組・1 語でしか `b_freq` を照合していない、など)。

## 進め方

1. 設計書を書く(1 ファイル・新規)。
2. **数を書くときは数え方を併記**する(今日 4 回、数え方の違いで食い違った)。**`sha`・`digest` には版を併記**(CLAUDE.md の新規約)。
3. 書いたら**自分で照合する** — 引用した件数・語・`status` を現物と突き合わせ、**母数を先に固定**してから「すべて」と書く。
4. `rep` で coord へ初稿を知らせる。`status: open`・`needs_user_approval: yes`(設計の中身は利用者承認が要るため)。
