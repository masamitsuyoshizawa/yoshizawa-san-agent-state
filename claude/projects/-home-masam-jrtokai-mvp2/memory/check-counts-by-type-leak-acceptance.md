実の読取の出力に当てた検査(投入の門 K2・K3 など)の件数は、違反の件数であっても、要素の種類ごとの内訳(Section が何件など)を連絡文と docs に書かない。受入の期待は「章・節の数」「節見出しの全数」を照合するので、種類ごとの不一致の件数はその下限を示す。

**Why:** 2026-10-30、kgb が実の 2 文書の演習の info と検討記録に K2 の不一致の件数と Chunk・Section の内訳を書いた。K3 の件数は「総数と同じになる」ので伏せたが、K2 の内訳は見落とした。coord の指摘で、main に入る前にコミットを置き換えた(53e2698 → acef03f・利用者の確認の後)。

**How to apply:** acc が期待を凍結する(sha を info で出す)まで、実の入力に当てた検査の結果は「0 / 0 でない」と、当たった要素の種類の有無と、理由の種類だけを書く。件数は画面でだけ利用者に伝える。合成の入力の件数は書いてよい。関連: [[remerge-main-before-writing-comms]]

**追補(2026-10-30 23:1x・coord の注意):** 合否のそばの括弧の説明も値になりうる。「K4 の寄らない参照 0(参照が無い)」は、読取の出力に参照の辺が無いこと(接続の数の値)を示す。凍結までは、門と規則の合否と 0 だけを書き、「なぜ 0 か」の中身(辺や要素の有無・種類)は書かない。info 1606 と 2310 に出たものは、coord の判断で直さない。

**追補 2(2026-10-30 23:5x):** 同じ型が dcr の info 2344 §4 にも出た(守りの「当たり 0」の括弧が、説明書に表・セル由来の要素が無いことを示した)。coord は取り込みの読みで見落とし、kgb が気づいた。coord が取り込みで連絡文を読むときは、件数だけでなく「0 の理由の括弧」も、要素や辺の有無・種類を示していないかを見る。leak_check はこの型を拾わない。
