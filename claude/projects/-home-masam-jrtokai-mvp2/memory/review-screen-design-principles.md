利用者に頼む確かめは、`docs/08_人手確認の基本ルール_20261114.md`(第 1 版・決107)で行う。決104 §4 の 7 つは、これに置き換わった。

1. 人手確認は、開発の最大のボトルネックである。省かない。効率を最大にする。効率化に開発の手間をかけてよい。
2. 開発の時の確認の目的は、ノウハウを取ること(最終の結果を人が作ることではない)。同じ種類の判断を大量にさせない。代表の問い → 答えで機械を作り直す → 再確認、を徹底する。
3. サービスの利用の時の確認は、重要な誤りを通さない門。必要なデータの全部を見る。目的ごとに方法を分ける。
4. 画面: web(CSV・Excel でなく)・選んで答える(字を打たせない)・その画面だけで答えられる資料を出す・1 回 5〜10 分・意図と答え方を分かりやすく・合意の無い独自の語を使わず一般の用語・形をそろえる(回答は左、資料は右)。
5. 画面は、人に示す前に agy で点検する(合成のデータの見本で・顧客の資料は渡さない)。

**Why:** 利用者の指示(2026-11-14)。「人手での確認が、開発速度を遅らせる最大のボトルネック」。それまでも同じ所見が何度も出た(8735 の空の欄・8742 と 8735 の問いの意図・網と端の語・元の文書を横に・同じ記号が散らばる)。

**How to apply:** coord は、画面の配りの rep を取り込む時に、docs/08 §9 の点検の結果と、数と見込みの時間があるかを見る。無い画面は利用者に案内しない。利用者の作業の一覧は、数と見込みの時間を添え、まだ配られていない画面を載せない。姉妹のプロジェクトには、統合管理のセッションへのメッセージで知らせた(向こうのリポジトリには書かない)。関連: [[acceptance-independence-no-element-kinds]]

**第 3 版(決127・2026-11-16):** R13 問いの名を問う物と合わせる・R14 問いが指す所を資料の上に印で・R15 語の定義を実の資料で決められる形で・R16 答えに要る物が最初の画面で見える・R17 選びに中身を書く・R18 問いを原本に見える物の言葉で立てる(作り手の処理の都合で問わない)・R19 新しい形の画面は 1 問の見本で先に確かめる・R20 任意の備考・R8 の但し書き(数と番号は機械の読みを見せずに問う)。点検表は C1〜C23。C15〜C19 は、作り手が実の回で、共通の部品 `scripts/review_ui/` の数えの口で照らす。agy の点検は合成の見本だけなので、実の資料との食い違い(名・定義・見え方)は見つけられない。完了の知らせの後に残りの回があることが 2 度あった(8735)。作り手に、答えを読む前に回のそろい方を数えさせる。機械の読みを見せて正誤を問う形で、わざとの誤り 4 のうち 2(1 だけずれた値)が見落とされた。

**第 4 版(決151・2026-11-18):** R21 並べて見比べる物は表で出す・R22 問いと一覧が挙げる行と物は全部、資料の上で見える(別の頁はその頁も続けて出す・間の文も)・R23 字が読める大きさで出す・§5 に実の回の数え(表の数・区切りの字の行 0・挙げた行が資料の上に在る数・読める大きさの問いの数)。点検表は C1〜C27。8735(階層の見本)で利用者が 2 度答えられず、3 度目は「分からない」が正しい答えだった(見本が別表の中の行を本文の内訳として見せた)。数えがそろっても、「挙げた親が原本の親と合うか」は数えられない。coord は、案内の前に、数えと、挙げた行が資料に在るかを、rep の字で確かめる。部品は `scripts/review_ui/` 0.8.2。

**第 5 版(決154・2026-11-18):** R24 機械の答えを比べる問いは、機械が読めている範囲から選ぶ・R25 画面をまたいで選びの番号と向きをそろえる・R26 画面をまたいで同じ物を 2 度問わない・R27「分からない」の問いを同じ形で出し直さない(機械の側の欠けなら、欠けを先に直す)。点検表は C1〜C31。R25〜R27 は jrtokai-phase12 の知らせから。coord は、案内の前に、今出ている画面と、番号の向きと、問う物の重なりを見る。docs/08 の sha16 は c173a5108d7212bf。
