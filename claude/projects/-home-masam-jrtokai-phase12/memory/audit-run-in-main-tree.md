監査(X13 静的検出など、ファイルシステムを走査する検査)は **本体ツリー `/home/masam/jrtokai-phase12` で回し、報告に回した場所を書く**。自分の worktree で回すと、本体ツリーにしかない git 管理外のファイルが見えない。

**Why:** 2026-09-24、`accident_kb_v7/scripts/ingest_batch.py`(ingest_one を直接 import する旧い B 一括投入)が 7 月から本体ツリーに git 管理外で置かれていたが、dkb は X13 を自分の worktree で回していたため 2 か月検出されなかった。X13 の実装(os.walk)は正しく、原因は回す場所だった。coord の `git add -A` で追跡が始まり worktree に現れて初めて FAIL になった。coord が規律に追加。

**ただし「コードの版」を確かめるときは逆**(2026-09-18 に判明)。**本体ツリー(main)は遅れることがある** —
この日、**main の `kg_api/app.py` は `3f325b4298d22aa4`(3,854 行)で、EC2 と coord/fed のツリーは
`8c067de908b192b0`(3,934 行)**、**main へ未 merge のコミットが 176 件**あった。**本測定(甲13-7)が
本番の版を凍結する間は main へ merge しない**という運用のためで、**この窓の間、本体ツリーの
`app.py` は本番と別物**である。**coord は本体ツリーの `app.py` から規則を読んで検算しており、
たまたま該当箇所が両ツリーで同一だったため結論は変わらなかった。**

**使い分け**: **git 管理外のファイルを走査する監査 → 本体ツリー**。**本番で動いているコードの版・中身 →
反映元のツリー(または EC2 の実体)**。**どちらを見たかを報告に書く。**

**How to apply:** 監査の報告に「回した場所」を書く。worktree で確かめた場合は、main に入った後に本体ツリーでも回す必要があると書く(dkb は本体ツリーの作業コピーを書き換えない)。関連: [[audit-fed-writes-fed-tree]]・[[dkb-audit-state]]

**逆向きの場面がある(2026-09-19)。自分の未コミットの変更を検証するときは、変更のあるツリーから回す。**

`norm_method` を足した演習で、変更は worktree(`jrtokai-phase12-dkb`)にあるのに `rehearse_env.py` を**本体ツリー(`main`)から回した**。`rehearse_env.py` は `copytree` で**スクリプトのあるツリー**から一時ツリーを作るので、**古いコードを検証して「合格」と出た**(`pipeline_rc: 0`・`canonical_unchanged: True`)。

**気づけたのは、報告の文言を自分の変更と突き合わせたから。** G13 が「検査 **4** 項目 PASS」と出ていた。私は **5** 項目に直したはずだった。**合否の指標(`pipeline_rc`・`canonical_unchanged`)だけを見ていたら気づけない。**

**どちらのツリーで回すかは「何を検証したいか」で決まる。**

| 検証したいもの | 回す場所 |
|---|---|
| **稼働している版の健全性**(監査) | **本体ツリー**(git 管理外を見落とさない) |
| **自分の未コミットの変更** | **変更のあるツリー** |

**データの版が混ざらないかは別に確かめる。** 今回は worktree の `knowledge_kb_v8/data` が本体ツリーと**同一 inode**(`stat -c "%d:%i"` で確認)だったので、「コードだけ自分の版・データは共通」になった。リンクでなければ、データの版も食い違う。

**How to apply(追加)**: **検証が通ったら、出力の中に「自分が変えた箇所」が現れているかを 1 つ確かめる。** 件数・項目数・版の文字列など、変更前後で必ず変わる値を 1 つ選んでおく。合否の指標は「走ったか」しか言わない。
