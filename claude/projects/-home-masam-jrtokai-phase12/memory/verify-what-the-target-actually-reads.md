2026-09-16、プロンプト `cypher_generation/v5.0.md` の写しを「3 か所で同じにする」と決めて揃えたのは誤りだった。**`kb_demo_v5`/`v6` が読むのは飯田線のグラフ(`Route` 14・`route_symbol` は `〇E` 等・文字飾りタグ移行の対象外)で、kg_api が読む関西線の `cgraph`(`Route` 495・タグ形)とは別のデータ**。3 か所に同じ写しがあるのではなく、2 つの別グラフを説明する 2 種類のプロンプトだった。

**coord・fed・ckb の 3 者とも「実データで確かめた」と書き、3 者とも同じ関西線グラフを見ていた。** fed(私)は「デモが `v5.0` を読む」経路を Dockerfile から `app.py` まで正しく辿ったが、**その先の接続先を見なかった**。気づけたのは「反映前後で同じ質問を 1 件投げて比べる」の反映前を採ったときで、返った system_prompt が飯田線のスキーマだったため。

**Why:** 「実データ」という語は、どのデータかを書かない限り検証にならない。経路の追跡は「どのファイルを読むか」までしか決めず、「そのファイルが何を説明すべきか」は接続先が決める。

**2026-09-19 に別の形で再発した。** B-KB の測定用フラグを設計し、既定を「本番の挙動」として `False` を置いたが、**その「本番」は手元の `main` のコードだった**。稼働環境は `dec` で **(1) あり(`82b2d82fa10a5059`)で凍結**されており、**私の撤去実装(`942901742392c56a`)は反映が保留**されていた。既定 `False` のまま反映すれば、指定しない利用者が**採否の決定前に**新しい挙動へ変わる設計だった。外部レビュー(rev)の指摘で気づいた。**手元の HEAD と稼働中の版が違うのは、反映が保留されている間はむしろ通常の状態である。**

**2026-09-24 に 3 度目。** 「設備辞書の生成入力(`term_index.json` ほか)を `pipeline_manifest.json` の統制に足す」という提案に、**「辞書を生成し直すときだけ照合し、投入の G0 は変えない」という条件つきで合意した。** だが **G0 は manifest の `files` を全件照合する**実装で、**同じ鍵に足せば索引の更新で B の投入が止まる**。私は「足す先」を確かめずに、足し方の意図(生成時だけ効く)が実現できる前提で合意していた。coord が現物を読んで見つけ、別の鍵 `dict_inputs`(G0 は読まない)を新設する形に直した。**提案の意図と、その提案を受ける仕組みの挙動は別物である。**

**2026-09-24 に 4 度目**(**今度は上流の決定文を写して**)。 coord の `dec` が「公開された release の集合 `P` は台帳から得る」と書いたので、**自分の計画にもそのまま書いた**。**台帳はファイルで、DB の read transaction の中では読めない**(公開済みの最大 1 つと 4 鍵しか持たない)ため、`P` は台帳から作れない。dkb が指摘して訂正された。**自分の担当は「読む側の条件」で、その値がどこから読めるかは自分で確かめるべきところだった** — **上流が書いたから、では確かめたことにならない。**

**How to apply:** 実測を報告に書くときは**グラフ名・件数・接続先**を併記する。**「本番」「現行」「既定」と書く前に、稼働している版の識別子(sha 等)を取り、手元の HEAD と突き合わせる**(git から復元して sha を比べれば足りることが多い)。**反映が保留中・承認待ちの変更があるときは、手元のコードを基準にしない。**反映や一般化の前に、**反映先を実際に動かして**何を読んでいるかを確かめる(起動スクリプトの既定値を与えてクライアントを作り、実際に問い合わせる)。「A も B も同じはず」と揃える判断の前に、A と B の読み先が同じかを先に確かめる。違ってよいものは理由と結び付きを宣言し、各々が読み先と整合しているかを機械で検査する。関連: [[artifact-self-report-not-trusted]]・[[estimates-not-labeled-as-measurements]]・[[verify-zero-counts-before-reporting]]・[[hash-match-not-completeness]]

**関数を全件に当て直すときは、本番がその関数に渡す欄を写す(2026-10-01)。** D-KG の測定 1,716 件に `_safety_mark` を当て、未確認を 1,641 と報告した。backend は測定の名を `m.name` から渡す(`RETURN m.name AS item`)のに、dkb は欄名 `item` に引かれて存在しない `m.item`(全件 null)を読ませていた。正しくは 1,633。fed が別の数え方で食い違いを見つけた。**関数の引数名と DB の欄名は違うことがある**。当て直す前に、本番の呼び出し箇所の `RETURN … AS …` を読み、その欄が全件で空でないかを 1 行で数える。
