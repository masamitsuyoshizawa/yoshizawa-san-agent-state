**仕様は、実装して実データに当てるまで検証されない。** **レビューを何巡受けても、仕様だけを読む限り欠落は出ない。**

2026-09-18、B-KB の `graph_digest` の仕様(§6-1-1 の擬似コード + 正準化の契約 9 項目)は、rev のレビューを **2 巡**受けていた。coord も **2 回**読んでいた。実装して B 正本に当てた **最初の 1 回**で、欠落が 2 件出た。

| # | 欠落 | 規模 |
|---|---|---|
| (1) | **区分の列挙に 4 ラベルが無い**(`LogEntry`・`Document`・`RailCategory`・`SignalCategory`) | **18,243 ノード = 全体の 67%** を digest が見ていなかった |
| (2) | **`Document` が `id` を持たず、「`id` の昇順」で順序が決まらない** | **700 件**が同じ鍵。並びは DB の返却順まかせ |
| (3) | **同じ 700 件で関係の端点が `NULL` に潰れ、繋ぎ替えが digest に出ない** | coord が**実装のコードを読んで**発見 |

**(2) では 3 回続けて同じ digest が出た。** **「3 回一致した」は決定性の根拠にならない**(返却順がたまたま安定していただけ)。

**Why:** 仕様の読み合わせは、書かれていることの整合しか見ない。**書かれていないもの(列挙漏れ)と、実データにしか無い性質(`id` を持たないノードが 700 件ある)は、読んでも出てこない。** 「未実装」の危うさは「記録が出ない」ことではなく、**「仕様の誤りが見つからない」**ことのほうが大きい。

**How to apply:**
- **測定や判定の前提になる道具は、仕様のまま置かない。** 小さくてもいいので実装し、実データに 1 回当てる。
- **全件が過不足なく 1 回ずつ数えられることを検算する**(区分ごとの件数の合計 = 総件数)。列挙漏れはこれで出る。
- **「N 回一致した」を決定性の根拠にしない。** 鍵が一意かどうかを直接確かめる。
- **未知の区分・未定義の組合せが現れたら止める**検査を、生成と同じ場所に置く。「保証できない」と書くだけでは、違反があっても処理は回る。

---

**原因を 1 つ直したら、その原因が効く場所を全部数える。**

上の (2) を直したとき、**ノード側しか見なかった。** 同じ原因(`id` の欠落)が関係側にも効く((3))ことに気づかず、coord の指摘で初めて出た。

**How to apply:**
- **原因を言葉にしたら、その言葉で文書と実装を grep する。** 「`id` を持たないノードがある」なら、`id` を使っている箇所を全部出す。
- **見つけた場所だけを直して閉じない。** 同じ日に「同じ内容が複数の節にあるとき片方だけ直す」型も踏んでいる(門の境界・12 欄と旧式)。根は同じ。

**数だけの仕様(「6 欄の組」「N 件」)は、欄の名を書くまで実装できない。起草者自身が取り違える。**

2026-09-24、V3 語彙 DB の設計書は `PhenomenonClaim` の `id` を「6 欄の組から作る」とだけ書いていた。**その設計書を書いた自分が**、検算のときに `state`(実在しない欄)を入れ `status` を落とした。値が合わずに気づいた(null の数が 1,294 でなく 2,187 になった)。**現象辞書の鍵は 7 つで、外すのは `b_freq` の 1 つだけ** — 「6 欄」という数は正しいのに、どの 6 つかは数から復元できない。

**同じ日に 2 件目**: 設計書は `§2-2` から 1,200 行にわたり「`parent` を関係へ写す」と書きながら、**写した先の関係の名をどこにも書いていなかった**。共通表が挙げる関係 8 つにも無い。`PART_OF` は別名の `kind` から写す別物。**印を辺に持たせようとして初めて気づいた**(`HAS_PARENT` を新設し関係 8→9)。動作・件数・効果はすべて書いてあり、**名前だけが無い**。

**Why:** 数も動作も検算できるが、そこからは対象が決まらない。**書いた本人ですら数日後には引けない**ので、「レビューで気づく」より前に実装で詰まる。レビュー 3 巡も rev の 1 巡目も、この欠落を出さなかった — 読む側は名前を補って読むため。**並び順も同じ** — 列挙の順が変われば `id` が変わるのに、「6 欄」には順が入っていない。

**How to apply:** 仕様に集合を書くときは**要素の名を全部書く**(数の併記は検算用)。**順が結果を変えるなら順も仕様の一部だと明記する。** 「N ラベル」「N 欄」「N 件」と書いたら N の中身を同じ場所に並べる。**「X を Y へ写す」と書いたら、写した先の識別子(関係名・ラベル名・欄名)をその場で書く。** 自分の文書を読み返すときは、**動詞ではなく名詞を数える**(何が新設されるのか、その名は何か)。

**2026-09-24、同じ文書の中で「撤回が参照側に届かない」形が出た**(第 2 段の API 計画)。**誤った判定式**(`since` / `until` を対称に扱うガード)**を撤回して共通式へ置き換えたのに、要約の節と別表の 2 か所に古い判定が残っていた。** rev が現物を読んで見つけた。**撤回を本文に書いても、その語を参照している場所を直さなければ、文書は古い規則を主張し続ける。** 同じ回に、応答の欄の形を**実装を見ずに**書いていたのも見つかった(`vocab_files` を「`name` / `sha16` / `canonicals`」と書いたが、現物は `path` / `resolved` / `sha16` / `bytes` / `canonicals` / `state` の 6 鍵)。

**How to apply(2026-09-24 に足した 2 つ):**
- **撤回したら、その語で全文を grep してから出す。** 本文に「撤回した」と書くだけでは参照側に届かない。
- **欄の形を書くときは、その場で実装を呼んで現物を出す。** 記憶や前の文書から写さない。
