M01 の集計表に「現行の dkg は freq_* を LOO で数え直していない」と書いた。根拠にしたのは、点数の式(dkg_backend.py 134 行)だけだった。実際には後段に `_apply_loo_exclusion`(178 行・2026-08-26 導入)があり、exclude_ids を渡すと必ず差し引く。この記述を前提に、利用者が是正を決めてしまった(決244 (3))。是正の依頼を読んで実装の場所を探したときに気づき、取り下げられた(追補 1)。読むだけで測ると、残るずれは引きすぎ 98/647 問で、候補の上位 5 は全問で同じだった(決245 で「是正しない」)。

**Why:** 「無い」という主張は、経路の一部を読んだだけでは成り立たない。しかも利用者の判断の前提に直接なる。

**How to apply:** 「〜していない」「〜が無い」と書く前に、対象の値(例: freq の fc/fp/fi)を grep で全部たどる。読むのは、値を作る所・書き換える所・応答に出す所。書き換える関数があれば、それがどこから呼ばれるかも確かめる。[[assumed-current-state-without-checking]] [[claim-wider-than-implementation]] [[verify-zero-counts-before-reporting]]

追記(2026-10-28・bkb): 関数だけを読んで帰結まで主張した同型。`ingest_one._sup_load` は補完辞書が無いと空を返す(関数としては真)から「無いと既知の氏名が全部候補に出る」と dkb・coord・fed・利用者に報告したが、`ingest_one` は読み込み時に `name_scrub` を import し、それが同じファイルを読み込み時に読むので、無いと import で止まり帰結は起きなかった(info 20261028-2209 で訂正)。**帰結を書くときは、その関数に届くまでの import 時の副作用と呼び手の経路まで読む。**

追記(2026-10-29・dkb・決334): 「READ 包みの受入の R-8・R-9 は無い番号」と coord に報告し、決334 に追補まで入った。実際は dkb 自身の受入設計 §3-4 が R-8・R-9 を定義していた。grep の出力を `cut -c1-160` で切って表示したため、同じ行の後ろの定義を見落とした。**番号や項目が「無い」と書く前に、その項目を定義しうる文書を全部挙げ、切らずに読む**(表示を切る道具は見落としの元)。受入の項目が 2 つの文書に分かれるときは、道具で両方から取り出して和がそろうことを照らす。

**経路の順でも同じ(2026-10-29・fed・E4)**: 「intake のルータは include_router の最後 = 既存の口の照合は増えない」と、app.router.routes を列挙せずに書いた。実物は、app.py が @app で宣言した 17 経路が include の後に並び、FastAPI 0.139 の _IncludedRouter は中の経路を 1 本ずつ照らす(前置きの早抜けなし)= その 17 経路に 1 回 5.4 µs が足されていた。timer も「1 時間ごと」と書いたが、起動の直後に 1 回走る。**How to apply:** 「足される処理は無い」と書く前に、本物の app を起動して routes・user_middleware・threads・sys.modules を列挙し、条件(旗・設定)ごとに並べる。ループの本体を読んで初回の動きも確かめる。
