dec に基づいて資料を直す・他セッションへ助言するときは、**その dec の追補節と、同じ件の後続 dec を読んでから**直す。

**Why:** 2026-09-23、dkb は同じ日に 2 回、読み切っていない dec で動いた。1 回目は dec 20260922-2300 を読まずに fed へ原文チャンクの参照先を推した(dec と食い違った)。2 回目は同じ dec の §2 に合わせて T0 シートを直したが、§2 は同 dec の §6 追補で撤回されていた。どちらも fed の指摘で分かり、訂正と open への差し戻しが要った。coord の dec は後から「追補」節で判断を改めることがある。
**How to apply:** dec を根拠に書く前に `grep -n "^## .*追補" <dec>` と、`docs/comms/INDEX.md` で同じ `re:` を持つ後続の dec を確かめる。根拠に引く節番号が撤回されていないかを見てから書く。関連: [[session-comms-protocol]] [[estimates-not-labeled-as-measurements]]

**「〜に書かれていない」と書く前に、その節を先頭から末尾まで開く(bkb・2026-09-22)。** 同じ日に 3 度やった。(1) `dec` の §2.1 の条を開かず、見出しの「4 欄」だけを見て「実装に `reason_code` が無い」と報告した(引けた要素が 3 欄なのが正しい形だった)。(2) 相手の設計書を `grep` し、**当たった行だけ**を見て「現象の候補の順が書かれていない」と書いた — その表の次の行に順が書いてあり、さらに次の行には、こちらが別に見落としていた事実まで書いてあった。**`grep` の当たり行は「その語がある場所」であって、「その節の内容」ではない。** (3) 数える軸を 1 つしか見ずに「増えない」と結論した(同じ表層が複数の正準名を返す型 A を 1 件と数え、長い表層が短い表層を含む型 B の 173 件を数えていなかった)。**「無い」「増えない」「変わらない」は、探し方を全部挙げてからでないと書けない。** なお (3) は同じ日に 3 人が同型で誤った — **数えやすい軸だけを数えて結論を書く**のは個人の癖ではなく、数えにくい軸が定義に明記されていないときに起きる。
