T0 段階 1 のレビューで、同じ型が 4 回続けて出た(2026-09-16〜17)。**検査そのものは正しいのに、その検査が何を保証しているかの説明が実装より広い**。

- 「引用した見出しが実際に実行される」→ 実装は**否定例の列だけ**だった(Y2)。
- 是正後も**隣の肯定例の列**に同じ穴が残った。`c[5]` と**位置を手で書いた**ため(Y2b)。
- 「列ごとに役割を宣言した」→ **7 列中 4 列**で、照合も片方向(宣言 ⊆ 見出し)だったので**宣言を消せば検査ごと消えた**(Z1)。
- 「dkb の列は対象外」→ 実測すると、その表では**dkb の引用は dkb 列に 0 件**で肯定例・否定例にあった。**除いているのは列ではなく群**だった(Z1)。
- 「残るのは表も同時に書き換えた場合だけ」→ **表に引用されていない検査が 60 件あり**、そこは表を触らずに同数別名置換が通った(Z2)。

- 「その実装はまだ無い」→ **語を決めて grep しただけ**だった。`fingerprint`/「指紋」が 0 件なので「未実装」と結論したが、判断の対象そのものが**別の名前**(`graph_uris`)で既に在った。**`grep` の 0 件は「無い」ではなく「その語では見つからない」**。
- 「引数の注釈は 3 か所」→ **5 か所**だった(`*args`・`**kwargs` を落とし、その 2 つだけ黙って素通り)。**列挙の漏れには 2 種ある** — 種別の漏れは既定の再帰が拾って落ちないが、**特別扱いするノードの内部でフィールドを落とすと走査されずエラーにもならない**。
- 「この構文は素通りする」→ **静的な読取関数の戻り値だけを見て、道具を最後まで回していなかった**。実際に 3 段(群→生成→受入)を回すと `SyntaxError` で落ちていた。**`ast.parse` が木にしても `compile` が拒む構文がある**(PEP 695 の bound に `:=` は書けない)。しかも bound は**遅延評価**で、そもそも拾うべき位置ではなかった。**「拾えていない」と「拾わなくてよい」は別**。
- 「常設試験で決定論を担保した」→ **担保していたのは Python 側の構造と出力だけ**だった。**試験が DB を
  差し替える設計(`run_query` を注入)だったので、`Cypher` の文字列が妥当かを一度も見ていない**。
  **テンプレートを壊しても 13 件すべて PASS する**(2026-09-18・自分で変異を当てて実証)。
  **別の言語の文字列(Cypher・SQL・正規表現)は、その言語の処理系に当てないと妥当性が分からない** —
  **`EXPLAIN` の口を分けて足し、「DB へ到達しない」は合格にせず別の終了コードにした**。
- 「常設試験が通ったから実装は正しい」→ **試験が本番より寛容だった**。試験は関数を取り出して `import` を注入していたので通ったが、**本体には `import` が無く**、実行時は例外を握りつぶして空文字を返すところだった。**試験環境の甘さは欠陥を隠す**ので、「本体側に前提が在るか」も検査に入れる。
- 「rc=1 だから狙った検査で落ちた」→ **多段の仕組みでは、前の段で落ちると後ろの段に到達しない**。同じ rc でも、群の構文エラー・群の件数不一致・受入の検査は別物。**どの段で落ちたかを併記する**(判定語は推測せず、実際の出力から取る)。

- 「状態は 3 つあるので分けよ」→ **2 つは区別できなかった**(2026-09-19・監査台帳 (eeee))。
  **辞書に無い語が設備名かどうかは、辞書を使わずには決められない** — 決めようとすれば LLM に判断させることになる。
  **是正は「区別する」ではなく「分かっていることだけを名乗る」**: **辞書由来は「辞書に当たる語が無かった」だけを言い、
  正規表現由来は「質問に無い」と言ってよい**。**要素の出どころで「言ってよいこと」が違う。**
  **区別できないものを区別したように見せると、機械も人も誤る。言えないときは「どちらかである」と言う。**
  **指示された側が「区別できるか」を先に確かめたので止まった**(指示は過大だったが、(1) を分ける必要はあった)。

**共通する形**: どれも**1 段だけ見て結論している** — 理由だけ引き継ぐ / 条件を読まず行だけ見る / 語だけで探す / 戻り値だけ見て道具を最後まで回さない。

**Why:** 範囲を手で書くと、対象が増減しても追随しない。そして説明は実装より広く書かれやすい — 書いている側は「守りたいもの」を書き、実装は「書けた分」しか見ない。

**How to apply:** 範囲は定数や宣言から導き、位置(添字)で書かない。宣言と対象の集合は**双方向**に照合する(片方向だと宣言の削除に気づけない)。「どの列か」だけでなく「どの群か」まで名前に出す。広すぎる主張を見つけたら、**実装を主張に合わせる**(検査を足す)か、**主張を狭める**かを費用と保証で選び、選んだ理由を書く。**語で探す前に対象の現物を読む**(探す語を先に決めると、別の名前で在るものを取り逃す)。**結論を出す前に、その道具を最後まで回す**(部品の戻り値ではなく、実際の入口から end-to-end で確かめる)。**多段なら、どの段で落ちたかまで書く。**却下するときは「できない理由」ではなく**保証上の差と、それを許容する理由**を書く。関連: [[artifact-self-report-not-trusted]]・[[negative-test-check-reason]]・[[verify-what-the-target-actually-reads]]

**保証範囲は、実装だけでは決まらない。データの状態に依存する分は、状態が変わると消える(2026-09-19)。**

B 正本の投入で、G0 の「開始時ダイジェストが台帳と一致するか」という検査は、**実質的に「どの DB に繋いでいるか」も見ていた** — ローカルと EC2 で中身が違ったので、ローカルへ繋いで `--env ec2` と書けば digest が合わず止まった。

**その日の投入で 2 環境の中身が完全に一致し、その働きは消えた。** 実装は 1 文字も変わっていない。

**Why:** 実装から導いた保証範囲でさえ、「たまたまデータがそうなっていたから効いていた」分を含みうる。**実装を読むだけでは、その分を切り分けられない。**

**How to apply:**
- **検査が「何を区別できるか」は、区別したい対象の実データで確かめる。** 同じ値になりうる 2 つを、実際に両方測って違うことを見る。
- **中身で識別する仕組みは、複製で作られた環境では破れる。** 2026-09-19 の実測: EC2 の DB はローカルの dump 復元なので、`CALL db.info()` の `id` も `creationDate` も同一。設定値(`server.directories.data` 等)も同じイメージなら同一。`SHOW SERVERS` は community 版で使えない。**複製されない識別子は、中身にも設定にも無い。**
- **識別は接続経路に頼るしかないが、SSH トンネル越しだと経路も `localhost` になる。** 経路が区別できる形(ポート公開など)になるまで、その検査は効かない。**「将来直す」ではなく「経路が変われば効き始める」と書く。**
- **効かないと分かった門を足さない。** 実測で不成立と分かったら、実装しないのが正しい。

**対称の型 — 受け取った答えも、問いより広く読まない(2026-09-21)。**

利用者が「V2の変更をもとに実装を始めた**エージェント**はありません」と答えた。これは A2-1(V2 の口を置き換えるか)の前提の事実として回された。**しかし答えているのはエージェントについてだけで、内部の呼び手(評価スクリプト・Dify プラグイン・薄いクライアント・他セッションの道具)には答えていない。** 置き換えの代償はそちらにも掛かる。リポジトリを探すと 0 件だったが、**探す前に「呼び手は無い」と読んでいたら、確かめる動機が消えていた**。coord も「この切り分けは私の dec に欠けていた」と認めた。


- **測定の軸を 1 つ固定したまま、固定していない範囲まで結論を書く**(2026-09-21・辞書の `parent` 是正): 依頼が「`alias_policy` の値ごとに測る」だったので方針の軸だけ動かし、**入口の語を「ポイント」に固定して測った**。その語は `status=proposed` で既定の方針では索引に入らず候補 0 になるため、「いまの既定では是正の効果は 0」と書いた。**入口を「分岐器」に変えると既定でも 23 → 50 語、「軌道回路」は 191 → 168 語で効いていた**(他セッション 2 人が別々に数えて一致)。**測定の設計を受け取ったら、動かした軸だけでなく固定した軸を結論に書き添える**(「いまの既定で『ポイント』から引いたときは 0」)。同型は 2 度目 — 1 度目は、表層を同一視する模型で測った 141 語を、`id` を節点にする自分の設計の値として報告した。**どちらも「測った条件より広い範囲について結論を書いた」形である。**
**How to apply:** 他者の回答を前提として引くときは、**問いの語をそのまま範囲として書く**(「エージェントについての回答である」)。広い語(「呼び手」「利用者」「全部」)へ言い換えない。**言い換えたくなったら、その差が自分で確かめられる範囲かを見る** — 確かめられるなら確かめ(grep の 0 件は「その語では」と添える)、確かめられないなら「見えない範囲」として限定に書く。

**渡す定義が、受け手の持ち物だけで閉じているか(2026-09-21)。** `vocab_digest` の符号化を書くとき、対象ファイルの順を「`VOCAB_SOURCES` の順」と書いた。受入の側(bkb)は**実装を開かない**約束(共通表 §1-4 の E1「テンプレートを複製させない」)なので、この定義では独立に計算できない。**独立性を求める規則を守りながら、定義の一部を実装の定数に残していた**。bkb が文だけから 1 度組んで見つけた。是正はパスを literal で書くこと。同じ便で、規則そのものの版(`vocab-digest-v1` の札)も欠けていた — **規則を変えたとき、旧い値と新しい値が同じ形の 16 進で並び、区別できない**。

**How to apply:** **相手に独立に作らせる値は、「相手が持っている物だけ」で定義が閉じるかを確かめてから渡す**(相手のツリー・相手が読む文書・相手が開かないと決めた物を並べる)。**規則そのものに版の札を付ける**(出力だけ見て規則の版が分かるように)。**閉じているかは、相手が文だけから 1 度組んで値を突き合わせると分かる** — 3 人が別々に組んで同じ値なら「文が同じ意味で伝わった」が言えるが、**規則の正しさの独立の確認ではない**(書いた本人が混ざっていればなおさら)。

**一度きりの手動確認を「検査が守っている」と申告する(2026-09-21・V3 段 5)。** 報告の「どの契約を、どの検査が守るか」の表に、`契4 → (l1)(l2)(実 HTTP)で 8 通りを投げる` と書いた。**(l1)(l2) は `limit` しか投げず、契4 の実 HTTP の検査は試験ファイルに 1 つも無かった** — 実装中に対話の中で手で投げて確かめただけだった。**受け手(coord)が 15 通りを投げて `null` の抜けを見つけた**。抜けたのは、当方が投げた 8 通りに `null` が無かったからで、**試験に残していれば、自分でも他人でも数えられた**。

**Why:** 手で確かめた記憶は「確かめた」として残るが、**再現しないので、何を投げたかの一覧が残らない**。表に書く時点では「確かめた」しか覚えていないため、実在しない検査名を根拠として書いてしまう。

**How to apply:** **「どの検査が守るか」の表を書いたら、検査名が試験ファイルに実在するかを 1 件ずつ `grep` で確かめてから出す。** 手で確かめたものは「手で確かめた(試験には無い)」と書くか、**その場で試験に残す**。受け取る側も同じ照合をする(coord は以後そうすると返した)。
