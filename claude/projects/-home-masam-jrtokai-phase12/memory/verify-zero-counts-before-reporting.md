グラフ(Neo4j)の計測で「0 件」「到達しない」を報告する前に、使った関係型名・ラベル・向きが実在することを `CALL db.relationshipTypes()` / `db.labels()` で照合する。到達数は**完全有向**の値で主張し、逆向きを許した値は「逆向きを許せば」と条件を明記して別に書く。

**Why:** 2026-09-15 の障害探索ツリー第 3 段で、fed が存在しない型名 `NORMALIZED_AS`(B 側の型名。D-KG は `NORMALIZES_TO`)で数えて「症状→検査 0 件・木が 3 段で終わる」と報告し、同じ rep 内で正しい型名を括弧で注記しながら表の値を 0 のまま残した。正しくは完全有向で症状 195・検査 297 に到達。利用者の承認事項の前提になるところを coord の検算で止めた。dkb も同時期に無向探索の値(579)を有向の到達として報告しており、同型の誤り。評価レポートで「記録なしと 0 を区別する」方針を採りながら、自分の計測には同じ規律を当てていなかった。

**How to apply:** 汎用の規律(到達数は「無向・型無制限(上限)」と「型限定・向き固定(実効)」を必ず並べる/逆行は型ごとに式に書く/端点の型を全列挙してから経路を定義する)は `docs/comms/COORDINATOR.md` L16〜 に 3 者共通の規律として記録済みなのでそちらを正とする。ここに残すのは fed 固有の注意: 0 や到達なしが出たら、(1) 型名・ラベルの実在照合 (2) 向きを変えて再計測 (3) 注記と表の値が矛盾していないか確認、の 3 点を済ませてから報告する。B(9890)と D-KG(10090)は同じ意味の関係でも型名が違う(`NORMALIZED_AS` 534 本 / `NORMALIZES_TO` 258 本)。承認事項を含む rep は特に、1 つの見方で数えた値を別の見方で確かめる。**集合が同じかは件数でなく要素(elementId)で比べる**(2026-09-15: 件数 175 の一致から他者の式の出どころを推定して外した。175 は 3 つの無関係な集合に現れていた)。MATCH を 2 つに分けると関係一意性が効かず別の集合になる点は COORDINATOR.md 規律 4。関連: [[fault-tree-stage3-fed]]
