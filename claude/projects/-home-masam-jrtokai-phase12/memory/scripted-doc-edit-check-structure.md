**How to apply:** 文書をスクリプトで書き換えるときは、行単位で範囲を決めて置き換える(複数行の正規表現に re.S を使わない)。置換ごとに `assert old in s` で当たりを確かめ、書き込み後に見出し数・行数・表の行数を前後で比べてから報告・コミットする。[[hash-match-not-completeness]]

**追補(2026-09-16・コードでも同じ)**: テストの自己検査を差し替えるとき、置換の範囲(開始と終了の目印の間)を広く取りすぎて、間にあった既存の自己検査 2 件を巻き込んで消した。前後で**件数と見出しの集合**を比べて気づいた。文書の見出し数・行数と同じで、コードでも「置換の前後で検査の件数と名前を比べる」を習慣にする。

**同じ根の別の事故(2026-09-26)**: heredoc の中の Python スクリプトで、置換後の文字列に `"\n# 見出し…"` と書いたつもりが、**シェルがバックスラッシュを解釈して生の改行になり**、文字列リテラルが閉じずに `app.py` を構文エラーにした。`git checkout` で戻し、**改行を含む文字列を使わない設計**(併記を 1 行で足す)に変えて入れ直した。

**連絡文をシェルの heredoc で書かない(2026-09-19・同日に coord と 2 人が踏んだ・監査台帳 (nnn))**:
`cat > f <<MD` のように**クォートしない heredoc** だと、本文中の **`` ` `` がコマンド置換として実行され、
`ORDER BY` や `LIMIT` のような語が**空文字に置き換わったまま投函される**。**エラーは出るが本文は書かれる**ので、
中身を見ないと気づかない。**書き直すときに Python の `%` 書式を使うと、今度は本文中の「84.7%」と衝突して落ちる。**

**How to apply(連絡文・記号を含む長文)**: **Python から書き、置換は `.replace("__SHA__", v)`**(**書式指定子を使わない**)。
シェルで書くなら **`<<'MD'` とクォート**する。**書いた後に、消えては困る語を 1 つ `grep -c` で数える。**

**表の行の直後に節を挿さない(2026-09-21・同じ型を 1 日で 2 回)**: Markdown の表の途中に `#### …` の節を挿し込むと、表がそこで切れ、残りの行が節の後ろに取り残される。**1 度目は §3-3 の応答の表、2 度目は §4-2 の段の表**。どちらも「その行の説明を近くに置きたい」動機で起きた。**節は表の後ろへ置き、表の中からは「下の §X-Y」と参照する。** 検査は「`|` で始まる行の塊ごとに、2 行目が区切り行か・列数が揃うか」を見る(**2 度目はこれで拾えた。1 度目は目で気づいた**)。**同じ日に coord も同型を 1 件(表の行を空行で表から離した)出し、同じ機械検査で見つけて直した** — **個人の不注意ではなく、表へ追記する作業そのものが持つ型なので、表を編集したら毎回この検査を回す。****表のセルにパイプを書くときは `\|` にする**(`{"confirmed|…": 3}` のような例で列が割れる)。

**How to apply(追補):** スクリプトでソースを書き換えたら、**書いた直後に `ast.parse` で構文を確かめる**(文書なら見出し数・行数)。heredoc の中では**改行やバックスラッシュを含む文字列を避け**、どうしても要るなら 1 行に収まる形へ設計を変える。壊れたまま次の作業に進まない。
