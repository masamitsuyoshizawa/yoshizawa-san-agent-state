## V3(2026-09-19 に起きた)— **前提が変わり、(a)(b)(c) は選択肢でなくなった**

**利用者の新しい前提**: **顧客が直接 API を触らず、エージェントが必ず介在する。** **エージェントは質問の意図を正確に読めないので、API 側で複数の意図を想定し、どの意図であってもそれに応じた回答を区別して返す。**

**したがって下の (a)(b)(c) は「どれかを選ぶ」ではなく「全部返す」が答え。** **設備の括り方に Layer(L0 装置 / L1 部位 / L2 型式)を設け、切り口(3 → 6)と直交させる(最大 11 通り)。**

**当方が出した指摘(coord が採用・顧客への第 2 便へ反映)**:

**「全部返す」は甲13 で使った指標の形を構造的に壊す。** **返す量を増やせば再現は必ず上がるので、再現だけで評価すると「増やす」が常に勝つ。** **また前提上「当たらなかった切り口」は誤りではないので、従来の Precision が定義できない。**

**測るなら 3 つ要る**: **(i) 正しい解釈が含まれるか(議論はここに寄っていた)・(ii) 解釈どうしが区別されているか・(iii) 余計な解釈が多すぎないか。** **(ii)(iii) は顧客の言葉「区別して回答する」に含まれているのに測り方の候補が無かった。**

**Recall の定義が 3 通り**: **(甲) 切り口ごとに gold(最大 11 倍)・(乙) 和集合(必ず上がるので効果が測れない)・(丙) 顧客が選ぶ切り口(意図の推定が要り前提と矛盾)。** **測る前に決めないと後から有利な定義を選べる。**

**顧客へ聞くことになった**: **(iii) の上限(回答の長さ)と (ii) の定義(何をもって区別されていると言うか)。**
