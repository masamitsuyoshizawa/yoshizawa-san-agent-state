測定の成果物(JSON など)を別の道具が受け取って合否を出す形では、**受入側が自分の側に期待を持たない限り、成果物の中の欄どうしの比較にしかならず、生成側が一緒に縮めば黙って通る**。rev の第 6 次レビュー(2026-09-16・T0 段階 1)で 3 つの穴として出た。

- **群の集合**: 成果物の `probed` と `status.groups` を突き合わせても、両方から 1 群消せば通る。受入側の定数と照合する。
- **所定数**: 成果物が名乗った `expected` と `done` の比較では意味がない。**受入側が試験群のソースから宣言(`EXPECTED_CHECKS`)を ast で読む**。
- **欄の型**: 必須欄を型付きで要求する。文字列の `"3"` や真偽値の `rc` は「比較対象でない」として落とす。null を許す群は**受入側の明示的な例外集合**に限る。
- **失敗の境界**: 生成器は開始時に未完了の成果物を書き、前処理(import・入力の読込)の例外も失敗に落とす。公開は一時ファイル → `os.replace` で原子的。**実行識別子を持たせ、受入は完了した実行の成果物だけ受け取る**。群のループだけを try で囲うと、古い成功の成果物が残る。
- **識別子の重複**: 件数で終了を判定するなら、同じ見出しの 2 回目を失敗にし、一意数の一致も見る。でないと欠けた検査を重複で埋められる。

**Why:** 「検査はあるが守るべきものを守っていない」型の最終形が、この自己申告である。件数・成否・完了のどれも、生成側が書いた値をそのまま信じると、退行が起きても数字だけ揃って通る。

**対になる規律: 渡す側は「どこで測ったか」を 1 行書く。**

2026-09-19、B-KB の測定で「同じ設備が別ノードに割れるので 1 事故が複数行になる。`受信器` は 52 事故 → 96 行」と報告した。**その値は自分が手で書いた `MATCH (a)-[:INVOLVES]->(e) … RETURN a.id` で測ったもの**だったが、そう書かなかった。coord はそれを検算せず 2 つの文書へ写し、顧客向けの説明にも入りかけた。

**実際の生成 `Cypher` は 248 問すべてが `collect(DISTINCT …)` で事故ごとに畳んでおり、1 行 = 1 事故だった。** 自分のクエリの性質を、システムが生成するクエリの性質として一般化していた。**確かめる手段(生データの `cypher` 欄)は、報告した時点で手元にあった。**

| 誰 | 抜け |
|---|---|
| **渡した側(私)** | 出どころを書かず、自分の数値を自分で確かめなかった |
| **受け取った側(coord)** | 同じ生データが手元にあるのに検算せず写した |

**2 つで 1 組**: 受け取る側の照合(この memo の本体)だけでは、渡す側が出どころを書かないと照合すべき対象が分からない。**渡すときは出どころを、「直せ」と言うときは直す対象の現状を、それぞれ 1 行書く。**

**合意文書(dec)の文言も、自分の文書へ写す前に機構へ照らす。**

2026-09-24、V3 第 2 段で 2 回続けて起きた。どちらも coord の `dec` の一文が、指している仕組みでは成り立たなかった。

| 便 | dec の文言 | 機構では |
|---|---|---|
| 決29 | 「(i) の継続中は `meta` の `service_state` と `vocab_release` で読める」 | `service_state` は `ready` のままと fed が決めていた。**その欄からは継続中だと読めない** |
| 決30-3 追補 | 「`P` = 台帳の `published` の `release_ord` の集合(束の読込みと同じ read transaction で 1 回)」 | 台帳が持つのは**最大 1 つで集合でない**。**台帳はファイルなので DB の transaction では読めない** |

**1 回目は写してから気づいた**(自分の設計書に誤った一文が入り、rev の 2 巡目の固定版にそのまま載った)。**2 回目は写す前に気づき、`req` で返して dec 側が先に直った**。差は「dec を読むとき、指している仕組み(どの欄が何を持つか・どこから読むか)を思い出したかどうか」だけである。

**Why:** dec は合意なので、写すのが正しい振る舞いに見える。だが dec を書く側も現物を全部は見ていない。**自分の文書へ写した時点で、誤りは自分の主張になる**(出どころが dec であっても、読む人は設計書の記述として読む)。

**同じ目を自分の文書にも当てる。** 上の 2 回目(`P` は台帳から読めない)を返した直後の 3 巡目で、rev は**自分の設計書に失効した旧契約が 4 箇所残っている**ことを指摘した。`決30-2` で「digest の対象を束へ狭める」と決めた時点で失効していたのに、`VocabRelease` に digest・「履歴を含むので 2 回目は違う値」・`§7-3`・`§9` がそのまま残っていた。**他人の dec には「その欄は何を持っているか」を当てられたのに、自分の文書には当てていなかった。** 契約を変えたら、**変えた語(ここでは「履歴」「全プロパティ」「`graph-digest-apoc`」)で全文を grep し、1 件ずつ「失効か・説明として残すか」を決める**。

**How to apply:** 測定の成果物を作ったら「生成側が悪意なく壊れたとき、受入側は落ちるか」を 1 回考える。落ちないなら、受入側に独立の期待(定数・ソースから読む宣言・型・例外集合)を足す。効いていることは合成の成果物で対照する。**`dec` の一文を自分の文書へ写すときは、その文が名指す欄・ファイル・経路を 1 つずつ「何を持っているか」で確かめる。合わなければ写さずに返す。直す順は dec → 自分の文書。** 関連: [[hash-match-not-completeness]]・[[verify-zero-counts-before-reporting]]・[[estimates-not-labeled-as-measurements]]・[[ingest-effect-unmeasured]]・[[read-dec-addenda-first]]
