否定例(拒否されるべき入力)の試験は、起動不可・中止という結果だけでなく、**どの検査が何を理由に拒否したか**(エラーの検査コードと文言)まで確かめる。対応表の否定例には落ちた理由の札を付ける。

**Why:** 2026-09-24 の T0 段階 1 で、S1b の次を S4 に向け替える否定例を段階 1 の通常モードで回すと、承認済みの組の hash 不一致(V1・pin)でも落ちるため、向け替えそのもの(契約違反 V2c)を拒否できているかが分からなかった。試験モード(pin を見ない)で回して V2c だけで落ちることを確かめた。coord が「落ちた」と「意図した理由で落ちた」を分けるよう求め、対応表の否定例 49 件に札(抽出中止・実行時停止・評価拒否・契約違反・pin・自己点検)を付けた。

**追補(fed・T0 第 2 次是正 2026-09-24)**: 理由の確認に加えて、(1) **是正箇所を 1 か所ずつ戻した変異で該当の否定例が FAIL することを確かめる**(9 通り・coord が「いちばん重い内容」と評価。通ることの確認だけでは別の理由で落ちていても気づけない)、(2) テスト側は `rejected()` で検査の区分・理由の語・pin の有無を assert、(3) 札は推測せず `probe_ft0_reasons.py` でテストを流して観測して付ける。段階 1 の通常で pin で落ちたのは意図した 3 件だけだった。無条件で PASS する assert(`... if False else True`)を書いていないかも見直す。

**追補(fed・2026-09-27)— 変異が別の場所に当たる**: 文字列置換で変異を作るとき、**同じ形のコードが複数箇所にあると位置だけの置換が別の場所に当たる**。`_annotate_failure_terms` と `_annotate_equipment_terms` は本体が同形(`terms, _ = _..._terms(question)` / `if not terms: return question or ""`)で、`s.replace(..., 1)` が**前方の failure 側**に当たった。**`assert s2 != s` は通るので「変異が当たった」ように見え**、しかし equipment の試験は failure 側を見ないので**落ちない** — 「検査が効いていない」と「変異が当たっていない」が分離できていなかった。**関数名やコメントを含む一意な文脈で置換し、置換後に狙った関数が実際に変わったかを確かめる。** 変異で落ちなかったときは、まず変異自体を疑う。

**追補(fed・2026-09-27)— ソースに名前が在るかでは見ない**: 「その関数が呼ばれているか」を `"_annotate_equipment_terms" in acc_src` のような**字面の照合**で見ると、**実際の呼び出し(タプルの要素)から外しても docstring やコメントに名前が残るため通ってしまう**。設備名を外す変異・現象語を外す変異とも落ちなかった。**`ast.walk` で `ast.Name` として現れるものだけを採る**形へ直したところ、それぞれ担当の検査が落ちるようになった。**「在るか」ではなく「使われているか」を構文で見る。**

**追補(fed・2026-09-27)— 空集合への検査は常に真**: 「記録にある語がすべて併記に含まれるか」のような**全称の検査は、対象が空だと素通りする**。記録を消すだけで通ってしまい、実際「記録を常に空にする」変異で両方の試験が落ちなかった。**「対象の問いでは空でない」対照を必ず組にする。** 同じ理由で「呼び出しが 0 でも『外に無い』は成り立つ」ので、`accident` の外で呼ばれていないことを見る検査には「現に呼ばれている」を添える。**存在の主張と不在の主張は、必ず両方を要求する。**

**追補(fed・2026-09-17)— 変異の置換文字列は推測で書かない**: 変異を作るとき、置換対象をソースの見た目から推測して組み立てると当たらない。正規表現を `r"^[0-9０-９]+…"` のように `\uXXXX` で書いたソースに対し、全角文字を直書きした置換を **3 回試して 3 回外した**(`assert s2 != s` でしか気づけない)。**ファイルから該当ブロックを読み出し、その文字列オブジェクトそのものを置換対象に使う**と一度で当たった。

**追補(fed・2026-09-17)— 定数を参照した比較は、その定数を変える変異を捕まえない**: `body.count("・") <= ns["SYMBOL_EXAMPLES"]` のように**検査側が実装の定数を読んで比べる**と、定数を 3 → 99 に変える変異で**閾値も一緒に動いて素通り**する。**実数で比べ、定数がその値であることを別に assert する。** 同じ形は閾値・上限・件数の検査すべてに当てはまる。

**How to apply:** 否定例を書くときは、別の検査(hash の固定・承認状態・件数)が先に効かない条件で回すか、エラーの検査コードが期待どおりか(例: V2c だけで V1 を含まない)を assert する。他人のテストの否定例の理由は推測で付けず、所有者に付けてもらう。関連: [[hash-match-not-completeness]]・[[t0-stage1-trial]]・[[test-extracts-source-cut-by-syntax]]・[[annotations-must-read-original-input]]

**門を足すときは、その門が飛ばされる道が無いかを確かめる(2026-09-19)。**

台帳のキーを環境別(`b` / `b_ec2`)に分け、「`--env` の指定と実際の接続先が食い違ったら G0 で止める」検査を実装した。**検査の中身は正しく書けていた。**

否定例として `--env ec2` でローカルに繋いで回したら、**止まらずに完了し、`b_ec2` にローカルの値が書かれた** — 防ごうとした取り違えを自分で起こした。

**理由は「G0 が走らなかった」。** 状態ファイルの stem が日付単位で、`--env` を変えても直前の完了状態を**再開**し、G0 も本体の段も飛ばし、`finish()` だけが環境別キーへ書いた。

**私は門の中身ばかり見て、門が走るかを見ていなかった。**

**How to apply:**
- **新しい門を足したら、否定例を「実際に走らせて」止まることを見る。** 机上で条件を読むだけでは、その門に到達しない経路に気づけない。
- **飛ばされる道を数える**: 再開(resume)・キャッシュ・`skipped` 扱いの段・別のモード・別の入口。**どれかで門の手前を通過できないか。**
- **識別子(stem・キャッシュキー)に、分岐を決める引数がすべて入っているか。** 入っていない引数は「変えても同じ実行」と見なされる。今回は `--env` が stem に入っていなかった。
- **是正は、その引数を同一性に組み込む**(stem に含める + 状態ファイルに持たせて食い違いを拒否)。**門を強くするのではなく、門を飛ばせなくする。**

**逆向き — 「落ちない」を「見ている」と読まない(2026-09-21・V3 段 1 の枝の網羅)。** 試験がどの枝を守っているかを測るとき、枝を壊す変異を当てて「落ちない」と出たら、理由は 2 つある: **枝に一度も入っていない(未到達)**か、**通るのに検査していない**か。**到達の回数と変異の両方で測ると分かれる。** 実測では、`basename` のフォールバックは **18 回通るのに変異で落ちなかった**(= `resolved` を誰も見ていない)。到達だけを数えていたら「見ている」と読むところだった。逆に `read_error`・`parse_error`・「2 本だけ ok」は到達 0 で、検査を足す前に**その状態を作る入力**が要る。

**変異を測る道具にも対照を置く。** 複製へ実装だけを持っていき、前提のデータ(辞書)を置き忘れたため、**変異と無関係に 1 件が落ちていた**。「変異で落ちた」と読むところだった。**変異なしの対照を先に回して 0 件を確かめてから、変異を当てる。**

**変異をバッチで当てるときは、バイトコードの作り置きを毎回捨てる(bkb・2026-09-21)。** 同じディレクトリで変異を次々に当てて `python3 <試験>` を回したところ、**ある変異の結果が 1 つ前の変異の結果になっていた**(`span` を見なくする変異が「7 件落ちた」と出て、単独で当て直すと「1 件」だった)。**`__pycache__` の `.pyc` が再利用されていた。** 変異は秒内に連続して書かれるので、更新時刻と大きさによる無効化が当てにならない。**`shutil.rmtree("__pycache__")` と `python3 -B` を毎回入れる。** **落ちた検査の並びが 1 つ前と完全に同じなら、まずこれを疑う。**

**条件は実測で特定した(2026-09-21)**: pyc の古さの判定は**元ファイルの「更新時刻の *秒*」と「大きさ」**。変異はミリ秒の間隔で書かれるので**秒は必ず同じ**になり、**効いている条件は大きさだけ**。当方の 2 つの変異は、置換前が 44 / 43 バイト・置換後が 22 / 21 バイトで**前後とも 1 バイト違うのに、差がどちらも 22** となり、**ファイルの大きさが同じ 25,150 になった**。**「長さが変わっているから大丈夫」は、長さを実際に測っていなければ根拠にならない** — 手で 21 と 22 と数えて外した(実測は 22 と 22)。**差を測る。長さの印象で判断しない。**

**「落ちた検査 0 件」が、実は試験の例外死だった(2026-09-21・V3 段 5)。** 変異を 6 件当てて 2 件が「0 件」と出た。**構文は正しく、変異も狙った場所に当たっていた** — 試験が**その検査の手前で例外死**し、FAIL の行も後ろの検査も集計も出ていなかった(実施 31 / 32 で打切り)。原因は 2 つとも試験側:

- **`[0]` の取り出し**: `[f for f in facets if f["grouping"] == "grouped"][0]` が、組を減らす変異で空リストになり `IndexError`。
- **`detail` の先行評価**: `check(名前, 条件, "strict=%d" % e_s["..."]["count"])` の **`detail` は、条件が真でも偽でも呼び出し側で必ず評価される**。値を `None` にする変異で `TypeError`。**通っている間は気づけない。**

**変異を当てる道具の側に、集計の行(実施 / 所定 / 失敗)と `ast.parse` を出させて初めて、「落ちない」と「例外死」が分かれた。** **`assert s2 != s` だけでは、当たったことしか分からない。**

**等価変異がある — 「落ちない」が試験の欠陥とは限らない(同日)。** 「`grouped` は起点でも全 `kind`」の枝を壊す変異が落ちなかった。調べると、**検算の例の起点(分岐器)は全 `kind` も同義 3 種も同じ 15 語で、差が 0** だった。**出力が変わらないので、どんな検査でも捕まえられない。** 是正は検査ではなく**入力**: 差の在る起点(軌道回路・差 46 語)で見る検査を足した。**「合意された検算の例」が、その節の全部を確かめられるとは限らない。**

**実データで通らない枝は、合成の入力で見る(同日)。** 10 辺の打切りは、実辞書が下へ 4 辺しかたどれないため**一度も通っていなかった**(上限を 10 → 11 にする変異も、印を立てない変異も素通り)。**合成の鎖(辺 9・10・11・12)で境界の 4 行を期待値に持つ検査**を足して落ちるようになった。**閾値の定数は「実数で比べ、定数それ自体も別に assert する」**(検査側が定数を読んで比べると、定数を変える変異で閾値ごと動いて素通りする)。


**否定の例の「複製の上で」は、対象が変わっても外さない(bkb・2026-09-22)。** コードの変異では複製を使う規律を守っていたのに、**辞書**の否定の例(別名を 1 件外す・entry を消す・`_note` を足す)を**現物のファイルを書き換えて**当てた。戻したことを `git status` で確かめたので実害は無かったが、辞書 3 本は共有資源で「触らない」の対象であり、`LOCKS` の予約もしていなかった。**覚えた規律はコードに結び付いていて、対象が辞書・設定・データに変わると外れる。** 直し方は約束でなく道具で — 検査の道具に `--after-path` のような「複製を指す口」を先に作り、現物を既定にしたまま否定の例だけを複製へ向ける。**「次から気をつける」は、同じ型がもう 1 つの対象で再発する。**
